# Тест-план

Тестирование проектируем вместе с системой, а не после. Ниже — что проверяем на каждом уровне и что будет гоняться в CI на лабе 3.

## Уровни тестирования

### Unit (модульные)

Проверяем отдельные функции и модули агента.

- Парсер источников: правильно ли вытаскивает заголовок, ссылку, текст из статьи.
- Фильтр мусора и кликбейта: отсекает ли по ключевым словам.
- Ранжирование: ставит ли крупные события выше мелких.
- Валидация JSON: проходит ли ответ по схеме Pydantic.
- Подсчёт токенов: корректно ли считает стоимость.

Кто пишет: разработчик модуля.
Когда запускается: на каждый коммит локально и в CI.
Инструмент: pytest.

### Интеграция

Проверяем, как модули работают вместе.

- Сбор статей с 10+ источников → фильтрация → группировка → генерация дайджеста.
- Передача данных между шагами без потерь.
- Обработка ошибок: если источник недоступен — пайплайн не падает, а идёт дальше.
- Fallback: если LLM вернула невалидный JSON — перезапуск.

Кто пишет: разработчик пайплайна.
Когда запускается: на каждый PR в main.
Инструмент: pytest + mock-источники.

### Evals (оценка качества)

Проверяем качество ответа агента на Golden Dataset.

- Точность: нет ли галлюцинаций.
- Полнота: все ли важные события попали в дайджест.
- Релевантность: нет ли воды.
- Тон: кратко, по делу.
- Ссылки: у каждого пункта есть источник.

Кто пишет: вся команда, на основе `golden-dataset/cases.jsonl`.
Когда запускается: раз в неделю или перед релизом.
Инструмент: LLM-судья + ручная выборка.

## Что гоняем в CI на лабе 3

При каждом пуше в ветку:

1. Линтер (ruff или flake8) — проверка стиля.
2. Unit-тесты (pytest) — быстрые, до 1 минуты.
3. Проверка валидности JSON на тестовом запросе.

При каждом PR в main:

1. Всё из списка выше.
2. Интеграционные тесты с mock-источниками.
3. Прогон 5 кейсов из Golden Dataset (не все 30 — долго).

Раз в неделю по расписанию:

1. Полный прогон всех 30 кейсов Golden Dataset.
2. Замер метрик из `success-criteria.md`.
3. Отчёт в чат команды.

## Что не автоматизируем

- Ручную оценку релевантности (выборка 20 дайджестов).
- Проверку тона на спорных кейсах.
- Первичную разметку новых примеров в Golden Dataset.

## Правила

- Каждый критерий DoD либо проверяется машинно, либо переписывается.
- Тест-план держим на страницу, а не том на полке.
- Каждое поле ввода — потенциальная точка входа атаки. Валидируем всё, что приходит извне.
- Плохой эталон хуже отсутствия эталона: если сомневаешься в кейсе — удаляй, а не оставляй «как есть».
