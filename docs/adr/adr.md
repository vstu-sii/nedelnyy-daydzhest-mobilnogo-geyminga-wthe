## ADR-001. Пакетная генерация по расписанию, без реал-тайм

**Название:** Пакетная генерация дайджеста по расписанию

**Контекст:**
Дайджест выходит регулярно: weekly - раз в неделю (пятница/понедельник), monthly - в конце месяца. Возникает вопрос, как система запускает сборку: по внешнему запросу "здесь и сейчас" или по заранее заданному расписанию. В не-скоупе роадмапа зафиксировано: "Реал-тайм и ad-hoc генерация - только по расписанию".

**Решение:**
Пайплайн запускается планировщиком по расписанию. Тип выпуска (`weekly` / `monthly`) задаётся на старте и виден аналитику в шапке доски. Запуск "прямо сейчас" вне расписания не поддерживается.

**Цена решения:**
- Нет оперативной генерации по запросу - если аналитику срочно нужен внеплановый выпуск, он его не получит.
- Сбой окна сборки = пропуск выпуска или ручной перезапуск.
- Нужен отдельный механизм retry на стороне планировщика, иначе один сбой ломает весь выпуск.

## ADR-002. Ветвление пайплайна по типу дайджеста

**Название:** Единый пайплайн с ветками `weekly` / `monthly`

**Контекст:**
У двух типов дайджеста разная логика: weekly отбирает игры за неделю по топ-3 чартов + доп. критериям, monthly поднимает историю по проектам из топов и пересобирает оценку с трендом. Требуется решить: одна система с параметром типа или две отдельные системы.

**Решение:**
Одна система, две ветки логики, управляемые параметром `type` (`weekly` / `monthly`). Тип определяет отбор, глубину истории и логику динамики. Общие слои (сбор данных, рендер карточки, UI ревью) - единые для обоих типов.

**Цена решения:**
- Двойное покрытие тестами и guardrails - метрики считаются раздельно по каждому типу.
- Часть кода отбора дублируется между ветками.
- Риск расхождения веток при доработках: изменение в общей части может по-разному сказаться на weekly и monthly.

## ADR-003. Единый формат "белая доска" для обоих типов

**Название:** Единое представление - карточная доска

**Контекст:**
У weekly и monthly разный набор карточек и глубина истории. Требуется решить, будет ли у них единое представление или разные форматы вывода. В не-скоупе зафиксировано: "Отдельный формат для ежемесячного дайджеста - никаких других представлений".

**Решение:**
Единый формат для обоих типов - "белая доска" из карточек. Никаких таблиц, отчётов, side-by-side. Исторический контекст monthly упаковывается в тот же "квадрат" карточки.

**Цена решения:**
- Ограниченная гибкость представления: любые новые сценарии чтения потребуют новой доски, а не нового отчёта.
- Исторический контекст monthly сжимается в "квадрат" - объём истории на экране ограничен.
- Изменение шаблона карточки затрагивает оба типа сразу.

## ADR-004. 1-2 источника с приоритетным и резервным

**Название:** Два источника данных (приоритетный + резервный)

**Контекст:**
Среди кандидатов на подключение - SensorTower, AppMagic, Data.ai и соцсети. Требуется решить, сколько источников входит в MVP и делается ли сверка между ними. В не-скоупе: "Полное покрытие всех источников".

**Решение:**
MVP работает с 1-2 источниками: приоритетный + резервный на случай недоступности. Сверка между источниками не делается.

**Цена решения:**
- Приоритетный источник - единая точка отказа.
- Расхождения между источником и реальностью не отслеживаются автоматически.
- Расширение на остальные источники - отдельная переработка слоя сбора данных.

## ADR-005. Карточка как рендер-изображение по шаблону из 3 блоков

**Название:** Карточка - рендер "квадратика" по фиксированному шаблону

**Контекст:**
Карточка - единица дайджеста, "квадрат" с тремя блоками (шапка игры, описание, динамика метрик). Требуется решить, что является единицей рендера: живой HTML/компонент или сгенерированное изображение.

**Решение:**
Карточка рендерится в изображение по единому шаблону из трёх блоков. UI ревью правит данные, а не сам рендер; после генерации карточка не редактируется без перерисовки.

**Цена решения:**
- После генерации карточка не правится без перерисовки - правка описания = перегенерация изображения.
- Локализация и адаптивность затруднены (локализация - не-скоуп).
- Изменение шаблона требует перегенерации всех карточек выпуска.

## ADR-006. UI ревью как отдельный слой поверх пайплайна

**Название:** UI ревью - отдельный компонент, пайплайн его не знает

**Контекст:**
UC1 требует ревью и ручных правок, UC2 - только сборку. Требуется решить: встроен ли ревью-интерфейс в пайплайн или вынесен в отдельный слой.

**Решение:**
Пайплайн производит черновик и не зависит от UI. UI ревью - отдельный компонент: просмотр, правка категории/описания, публикация в один клик. Между ними - контракт через статус карточки `draft` / `final`.

**Цена решения:**
- Два контура состояния (draft/final) и необходимость их синхронизации.
- При рассинхроне возможна публикация устаревшего черновика.
- Пайплайн и UI развиваются раздельно - нужен контракт, который придётся поддерживать.

## ADR-007. Хранение истории проекта в persistent store

**Название:** История проекта - постоянное хранилище

**Контекст:**
Боль №3: аналитик вручную перечитывает старые выпуски, чтобы понять историю проекта. Требуется решить, где живёт история: пересобирается каждый раз из источников или хранится.

**Решение:**
История проекта - persistent store. Дополняется после каждого monthly-выпуска и читается в будущих карточках. Weekly-выпуски в архив сохраняются, но исторический контекст строится из monthly-истории.

**Цена решения:**
- Постоянный рост объёма данных, нужна схема версионирования.
- Ошибочный monthly может "загрязнить" историю и повлиять на будущие выпуски.
- Нужна логика обновления истории после выпуска, иначе хранилище рассинхронизируется с данными.

## ADR-008. Отказ от собственных ML-моделей в MVP

**Название:** В MVP только правила + LLM, без своих моделей

**Контекст:**
Среди рассматриваемых вариантов - обучение собственного классификатора категорий и модели поиска похожих игр для бирюзовой категории. Однако по insights гипотеза об авто-категории не подтвердилась полностью: категория требует экспертного контекста. Требуется зафиксировать состав компонентов.

**Решение:**
В MVP - базовые правила и LLM-суммаризация. Никаких обученных классификаторов на исторических данных, online-learning на правках аналитика, мониторинга аномалий.

**Цена решения:**
- Качество категории ограничено формализуемыми метриками.
- Обязательна ручная валидация категории, North Star напрямую зависит от объёма правок.
- При росте требований к точности - переход к отдельному ML-контуру (пост-MVP переработка).

## ADR-009. Статусная модель карточки `draft` / `final`

**Название:** Карточка имеет статус `draft` / `final`

**Контекст:**
Авто-категория не подтвердилась как надёжная (insights), финальное слово - за аналитиком. Требуется зафиксировать, как система отделяет автоматически присвоенное от подтверждённого человеком.

**Решение:**
Карточка имеет статус `draft` / `final`. Финальная категория не устанавливается без подтверждения аналитиком. Публикация переводит все карточки выпуска в `final`.

**Цена решения:**
- Ручное подтверждение спорных карточек снижает долю полной автоматизации.
- North Star (>=80% без ручной правки) напрямую зависит от объёма подтверждений.
- Нужна логика перехода статусов и её согласование между пайплайном и UI.

## ADR-010. Один уровень доступа в MVP

**Название:** Единый уровень доступа для аналитика

**Контекст:**
В MVP один пользователь - пилотный аналитик. Требуется решить, вводятся ли роли (аналитик / геймдизайнер / админ) сразу или откладываются. В не-скоупе: "Роли и права доступа - пост-MVP".

**Решение:**
В MVP - один уровень доступа для аналитика. Разграничение ролей - пост-MVP.

**Цена решения:**
- Нельзя разграничить доступ по ролям.
- Введение ролей - переработка контура аутентификации/авторизации.
- Геймдизайнеры получают дайджест через дистрибуцию, а не через систему - это осознанное ограничение.

## ADR-011. Дистрибуция ссылкой + экспорт

**Название:** Дистрибуция финального дайджеста - ссылка + экспорт

**Контекст:**
Дайджест должен доходить до геймдизайнеров и команды. Требуется решить, как именно: push в студийные системы, интеграции или базовый экспорт. В не-скоупе: "Интеграции и платформа".

**Решение:**
Финальный дайджест доступен по ссылке и экспортируется в Slack / PDF / email. Никаких внешних интеграций и мобильного приложения в MVP.

**Цена решения:**
- Нет push-доставки внутрь студийных систем.
- Интеграции и мобильное приложение - отдельный слой пост-MVP.
- Ссылка + экспорт как единственный канал - если команда не читает Slack/email, доставка не гарантирована.
