# Отчёт о нагрузочном тестировании

## 1. Цель тестирования

Проверить работоспособность Gaming Digest API и веб-приложения при одновременной работе нескольких виртуальных пользователей, оценить время ответа основных сценариев и поведение ограничения расходов.

Тестирование выполнялось локально с использованием Locust.

## 2. Конфигурация тестирования

Инструмент: Locust 2.47.0  
Среда: локальная Windows-машина, Docker Compose  
Пользователи: 5 и 10 виртуальных пользователей  
Пауза между действиями пользователя: 1–3 секунды.

### Проверяемые сценарии

| Сценарий | Описание | Вес |
|---|---|---:|
| UC1 | Открытие главной страницы | 5 |
| UC2 | Проверка состояния API и БД | 3 |
| UC3 | Получение метрик Prometheus | 1 |
| UC4 | Генерация игрового дайджеста | 2 |

Для UC4 создаётся уникальный идентификатор пользователя. Ответы HTTP 201 и HTTP 429 считаются допустимыми результатами сценария. Другие статусы регистрируются как ошибки Locust.

## 3. Результаты тестирования

### 3.1. Базовый smoke-тест

Параметры: 5 пользователей, 60 секунд.

| Показатель | Результат |
|---|---:|
| Всего запросов | 136 |
| Ошибки Locust | 0 |
| Запросов в секунду | 2,32 |
| Среднее время ответа | 16,54 мс |
| Медиана | 10 мс |
| p95 | 60 мс |
| Максимальное время | 63,46 мс |

Выполнено 21 обращение к сценарию генерации. При исходном низком бюджете запросы генерации достигали ограничения расходов и возвращали HTTP 429.

### 3.2. Smoke-тест с увеличенным бюджетом

Параметры: 5 пользователей, 60 секунд. Временный лимит расходов — 1 доллар.

| Показатель | Результат |
|---|---:|
| Всего запросов | 145 |
| Ошибки Locust | 0 |
| Запросов в секунду | 2,45 |
| Среднее время ответа | 21,75 мс |
| Медиана | 11 мс |
| p95 | 88 мс |
| Максимальное время | 110,75 мс |
| Запросы генерации | 27 |

По журналам API все 27 запросов генерации завершились HTTP 201.

### 3.3. Нагрузочный тест

Параметры: 10 пользователей, 120 секунд.

| Показатель | Результат |
|---|---:|
| Всего запросов | 583 |
| Ошибки Locust | 0 |
| Запросов в секунду | 4,91 |
| Среднее время ответа | 22,13 мс |
| Медиана | 10 мс |
| p95 | 85 мс |
| p99 | 100 мс |
| Максимальное время | 118,39 мс |

Распределение запросов:

| Сценарий | Запросы | Среднее время |
|---|---:|---:|
| UC1 — Homepage | 242 | 7,29 мс |
| UC2 — Health | 157 | 13,33 мс |
| UC3 — Metrics | 57 | 6,30 мс |
| UC4 — Generate digest | 127 | 68,38 мс |

По журналам API все 127 запросов генерации завершились HTTP 201.

## 4. Анализ результатов

1. Все четыре пользовательских сценария отработали без зарегистрированных ошибок Locust.
2. При увеличении числа виртуальных пользователей с 5 до 10 пропускная способность выросла с 2,32 до 4,91 запроса в секунду.
3. Основное время ответа приходится на сценарий UC4 — генерацию дайджеста.
4. Проверка состояния API и получение метрик выполняются быстро.
5. При достижении ограничения расходов приложение возвращает HTTP 429 вместо неконтролируемого выполнения запросов.
6. После временного увеличения бюджета генерация успешно выполнялась в рамках проведённого теста.

## 5. Выявленные ограничения и потенциальные узкие места

- UC4 имеет наибольшее время ответа среди проверенных сценариев.
- Тестирование проводилось только на локальной машине и не подтверждает производительность в production.
- Максимальная проверенная нагрузка — 10 виртуальных пользователей. Предельная пропускная способность системы не установлена.
- Используется локальная демонстрационная реализация модели, а не реальный внешний LLM-провайдер. Поэтому результаты генерации нельзя напрямую переносить на production.
- Не проводились длительный soak-тест, стресс-тест и отдельное измерение CPU, RAM и дисковой нагрузки.
- В тестовом сценарии используется уникальный X-User-ID, поэтому он не проверяет конкурентное поведение лимитов одного пользователя.
- HTTP 429 считается допустимым результатом Locust, поэтому нулевое число ошибок не означает, что каждый запрос генерации завершился HTTP 201.

## 6. Рекомендации

1. Провести дополнительные тесты при увеличении числа пользователей.
2. Контролировать время ответа и ошибки сценария генерации.
3. Добавить мониторинг CPU, RAM, PostgreSQL и пула соединений.
4. Для реального внешнего LLM предусмотреть таймауты, ограниченные повторы и обработку недоступности провайдера.
5. Проверить конкурентное выполнение запросов и корректность ограничений расходов.
6. Выполнить длительный тест стабильности после развёртывания в отдельной staging-среде.

## 7. Итог

В рамках локального тестирования приложение успешно обработало нагрузку до 10 виртуальных пользователей и 4,91 запроса в секунду.

В максимальном проведённом тесте Locust зарегистрировал 583 запроса без ошибок. Значение p95 составило 85 мс.

Механизм ограничения расходов также был проверен: при достижении бюджета API возвращал HTTP 429.

**Вывод:** проведённые тесты подтверждают работоспособность основных пользовательских сценариев в проверенной локальной конфигурации. Для определения реальной предельной производительности и готовности к production необходимы дополнительные испытания.
